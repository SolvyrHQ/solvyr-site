Fit

For teams with a real corpus backlog—and connectors who can spot one.

AI teams usually enter through output, price, and proof. Archives and public teams use the same bounded run while adding location, oversight, and sovereignty questions.

Good fit

  • Clean PDF or text batches with repeatable structure
  • RAG, search, evals, fine-tuning prep, or agent memory
  • Embedding refreshes and document re-indexing
  • Low- or moderate-sensitivity data that can be scoped safely

Not the current fit

  • Realtime product requests or open self-serve access
  • OCR-heavy scans without separate handling
  • Custom extraction or mature enterprise SLA needs
  • High-sensitivity data without a safe pilot sample

What makes a pilot timely

  • A backlog is blocking a RAG, search, eval, or agent project
  • The team wants a price before building its own pipeline
  • Corpus refresh will recur after the first run
  • An archive or public team wants European execution context

Common paths

  • Refreshing an embedding index
  • Reprocessing an archive into searchable chunks
  • Preparing clean PDFs for RAG
  • Creating inspectable corpus output for downstream AI work

How it runs

The corpus is the product. Controlled execution is how it gets done.

Solvyr matches bounded tasks to eligible compute, watches execution, retries within policy, and returns accepted output with run evidence.

One workload. The right compute path.

Compute can be distributed. Responsibility cannot.

The scheduler keeps authority over assignment, node eligibility, retries, result acceptance, and lifecycle evidence.

Organisation hardware Approved external node Specialised local capacity Central capacity Accepted output

Not a GPU marketplace

You do not provision workers, operate queues, or assemble the corpus pipeline.

Eligible execution environments

Solvyr-controlled capacity today; explicitly approved partner- or customer-controlled workers are a later path.

Measured, not assumed

Runtime, retries, accepted output, and resource use belong in run evidence—not in unsupported efficiency claims.

European execution context

Control becomes concrete when the workload is concrete.

For archives and public teams, execution and storage location, operator access, node eligibility, retention, deletion, and run evidence can be attached to an actual document batch.

Longer-term direction

Use the best eligible compute path for each bounded workload.

The direction is supply-neutral: existing organisational hardware, approved external nodes, future specialised local hardware, and centralised capacity when it is genuinely the right option. This is an expansion path, not broad current availability.

Security

Set the pilot boundary before the data moves.

For suitable low- or moderate-sensitivity work, define lifecycle, access, deletion, data minimisation, and execution context before the run.

What we can define for a pilot

  • Data lifecycle, retention, and deletion
  • Execution and storage location for the pilot
  • Input and output storage locations
  • Scoped operator access
  • Data minimization before execution
  • Payload logging checks
  • Temporary scratch cleanup checks

Current boundaries

  • No high-sensitivity workloads without a safe pilot dataset
  • No cryptographic privacy or confidential-compute claims
  • No broad enterprise compliance claim yet
  • No claim that distribution itself creates confidentiality

European execution context

Location and oversight belong in the pilot boundary.

For archive, public-sector, and European AI pilots, execution location, storage location, retention, deletion, and operator access can be made explicit before data is shared.

Risk reduction

Redaction or pseudonymization can be part of the pilot design.

We can help define pre-upload redaction or pseudonymization. Keep rehydration customer-side. Risk reduction, not guaranteed anonymity.

Scope boundary

Some data should not enter the pilot.

Some workloads stay out of scope. Suitable pilots get lifecycle, access, deletion, and execution boundaries before data is shared.

Security appendix

Topics to settle before a pilot run.

Data lifecycle
What is uploaded, produced, retained, deleted, and when.
Execution context
Where pilot work runs and where input, output, and scratch artifacts are stored.
Scoped access

Redaction

Logging and scratch
